# Design Acceptance Criteria

> Чек-лист для приёмки дизайна в Figma владельцем продукта **до** начала frontend. Пункт считается выполненным, только если его можно проверить в файле (кадр, компонент, переменная, аннотация). Состояние на момент написания — в §8.

## 1. Структура файла
- [ ] Ровно 3 страницы: `00 — Design System`, `01 — App Screens & Prototype`, `02 — Product Specs & API` (ограничение Starter).
- [ ] На странице экранов — Sections `01 Authentication` … `14 Flows` (DESIGN_SYSTEM_SPEC §10).
- [ ] Утверждённые v1-дашборды (`1:17`, `1:197`) сохранены без изменений в `02 Dashboard / v1 reference`.
- [ ] Именование кадров `{Экран} / {Light|Dark} / {Desktop|Tablet|Mobile}[ — {State}]`; нет слоёв с автоименами «Frame 123» на верхнем уровне экрана.
- [ ] Новые Figma-файлы не созданы.

## 2. Токены и темы
- [ ] Коллекции `1:2` (Light), `11:42` (Dark), `11:90` (Spacing & Radius) существуют; исходные переменные `VariableID:1:3…1:13` не удалены и не переименованы.
- [ ] Имена переменных в Light и Dark совпадают один к одному (29 + принятые дополнения D-1).
- [ ] Ни один экран не содержит захардкоженных цветов: проверка выборкой слоёв без `boundVariables` у fills и strokes, исключения — изображения.
- [ ] Каждый Dark-кадр — точная копия Light-кадра по структуре: одинаковое число слоёв и та же иерархия; отличаются только привязки к коллекции.
- [ ] Текстовые стили применены ко всему тексту экранов; семейство только Inter.
- [ ] Отступы и скругления привязаны к `space/*` и `radius/*`, где это предусмотрено.

## 3. Покрытие экранов (SCREEN_INVENTORY)
- [ ] Все **33 экрана** есть в Light и Dark на Desktop 1440.
- [ ] Экраны 🟧 (A-3, A-4, N-1…N-3) помечены бейджем «Требует backend», не связаны с рабочими сценариями прототипа и не показывают несуществующих данных как реальные.
- [ ] Экран S-2 «Оформление» помечен 🟦 (настройка хранится на клиенте).
- [ ] Для каждого экрана на странице `02 — Product Specs & API` есть аннотация: статус, эндпоинты, ссылка на `docs/design/SCREEN_INVENTORY.md#…`.

## 4. Состояния
Для экранов D-1, T-1, T-3, B-1, AN-1, AI-1, I-1 обязательно наличие кадров:
- [ ] Default
- [ ] Loading (скелетоны в форме контента)
- [ ] Empty (с главным действием)
- [ ] Error (с «Повторить» и местом для `request_id`)
- [ ] Validation errors (для форм T-3, B-3, G-3, AC-1 modal, DP-3, A-1, A-2)
- [ ] Success feedback (toast)
- [ ] Disabled controls
- [ ] Hover и Active (на уровне компонентов в Design System)
- [ ] Confirm dialog для удаления: операции, счёта, категории, бюджета, депозита, цели, отмены импорта; для «Выйти на всех устройствах»
- [ ] Специальные: 409 «счёт с операциями → архивировать»; AI `generated_by=rules` с причиной; импорт с `verified_parser=false`; бюджет > 100 %; `null`-показатели («—» с tooltip)

## 5. Соответствие API (критично)
- [ ] Ни одно поле на экране не отсутствует в API — кроме явно помеченных 🟦/🟧/⬜.
- [ ] Бюджеты показывают использование из `/utilization` или `overview.budgets`, а не `progress`/`spent` из `/budgets` (G-6).
- [ ] Заголовки таблицы операций **не** выглядят сортируемыми (G-7).
- [ ] Поиск операций подписан «Поиск по описанию».
- [ ] Обзор не предлагает выбор периода (G-23); аналитика — предлагает.
- [ ] Нигде нет итоговой суммы по разным валютам; есть переключатель валюты там, где это предусмотрено.
- [ ] «Денежный поток» и «Баланс» подписаны различимо; есть пояснение «не остаток на счёте».
- [ ] Депозиты различают «Номинальная ставка», «ГЭСВ (по данным банка)», «Эффективная годовая ставка (расчёт)»; показан текст допущений.
- [ ] Цель подписывает поле «Сейчас накоплено» (итоговое значение, не пополнение).
- [ ] AI-ответ показывает факты, допущения, дисклеймеры и метку «AI» или «Правила»; нет обещаний доходности или одобрения кредита.
- [ ] Форма счёта предупреждает, что валюту нельзя изменить, и запрещает полный номер карты (только последние 4 цифры).
- [ ] Валюта цели не редактируется после создания.

## 6. Контент и форматирование
- [ ] Весь UI-текст на русском; термины по глоссарию (DESIGN_SYSTEM_SPEC §9).
- [ ] Суммы в формате ru-KZ: `1 250 000,50 ₸`, минус — `−`, знак операции по типу.
- [ ] Даты `ДД.ММ.ГГГГ`, время 24-часовое, месяцы по-русски.
- [ ] Демо-данные помечены «Демо-данные»; нет реальных имён, ИИН, полных номеров карт и счетов.
- [ ] Тон поддерживающий, без осуждения за расходы или долги.

## 7. Визуальное качество и доступность
- [ ] Один и тот же сайдбар (компонент) на всех desktop-экранах; активный пункт соответствует разделу.
- [ ] Цвета графиков соответствуют порядку серий (§2.4); легенды, оси, tooltip есть у каждого графика.
- [ ] Мелкий текст статусов использует текстовые токены, проходящие AA (если D-1 утверждён); `text/tertiary` не используется для значимого текста.
- [ ] Видимый фокус на всех интерактивных компонентах (вариант Focus).
- [ ] Mobile: touch-цели ≥ 44 px, нет горизонтального переполнения, таблицы → карточки (RESPONSIVE_SPEC §4).
- [ ] Обязательные адаптивные кадры (RESPONSIVE_SPEC §3) — все 20.

## 8. Прототип
- [ ] Связаны сценарии: Вход → Обзор; Обзор → Операции → Детали; Обзор → Счета → Детали счёта; Обзор → Бюджеты → Детали; Обзор → Аналитика; Обзор → AI-советник; Обзор → Настройки.
- [ ] Переключение темы: кнопка в шапке ведёт на одноимённый кадр другой темы (navigate), потому что режимов переменных нет.
- [ ] Отчёт о приёмке перечисляет, какие взаимодействия **только изображены**, а какие действительно связаны в прототипе.

## 9. Расчёты для независимой проверки
Список — [BACKEND_GAPS.md §3](BACKEND_GAPS.md#3-требуют-независимой-проверки-финансовые-расчёты-backend). Дизайн их не меняет, но демо-данные в макетах должны быть **согласованными**:
- баланс = сумма показанных счетов;
- использованная часть бюджета ≤ показанных расходов категории;
- прогресс цели = накоплено / цель.

Цифры в демо-данных считаются вручную и сверяются при приёмке.
