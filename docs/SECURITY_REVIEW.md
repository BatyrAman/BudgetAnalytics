# Ревью безопасности и готовности к продакшну

Дата: 2026-11-18. Объект: backend (`backend/`), коммит рабочей копии.
Метод: чтение кода, целевые поиски по коду, тесты (включая мутационные проверки
защит), аудит зависимостей (`pip-audit`), учения бэкап/восстановление.

## Вердикт

**НЕ готово к продакшн-запуску.** Технические меры защиты на месте и проверены
тестами, но остаются блокеры (ниже). Готово к развёртыванию в **закрытом
staging** после зелёного CI и решения владельца.

## Блокеры продакшн-запуска

| # | Блокер | Тип | Что нужно |
|---|---|---|---|
| B1 | Нет юридической проверки: закон РК о персональных данных, локализация, трансграничная передача (в т.ч. в LLM-провайдер) | Правовой | Заключение юриста; до него `AI_PROVIDER=none` |
| B2 | Нет удаления аккаунта и политики хранения данных | Функц./правовой | Эндпоинт удаления/обезличивания + сроки хранения |
| B3 | Docker-образ и CI ни разу не выполнены в реальной среде (в среде разработки нет Docker) | Верификация | Прогнать CI на GitHub, собрать образ, поднять staging |
| B4 | Нет мониторинга и алертов | Эксплуатация | Сбор логов, метрики, алерты (5xx, readiness, диск, бэкапы) |
| B5 | Шифрование данных at-rest не обеспечено приложением | Инфраструктура | Зашифрованный том / управляемая БД с шифрованием |
| B6 | Парсеры выписок не проверены на реальных файлах банков | Функциональный | Обезличенные образцы Kaspi/Halyk/Freedom |
| B7 | Нагрузочное тестирование не проводилось | Эксплуатация | Нагрузочный тест критичных эндпоинтов |

## Результаты по категориям

### SQL-инъекции — защищено
* Все запросы — SQLAlchemy с параметрами. Поиск по `text(`, f-строкам с SQL,
  `exec_driver_sql`: только статические строки (`SELECT 1`, условия индексов).
* Единственная интерполяция — имя часового пояса в `literal_column`
  (`repositories/transaction.py`): проверяется `ZoneInfo` в API и regex-allowlist
  в репозитории. Риск: LOW.
* Поиск по описанию (`ILIKE`) экранирует `%`, `_`, `\` (тест `search=100%`).

### IDOR — защищено
* Каждый запрос к пользовательским данным фильтруется по `user_id` (проверено
  скриптом по всем `select(Model)`); чужой ресурс неотличим от отсутствующего (404).
* Ссылки на чужие категории/счета в транзакциях, бюджетах, импортах отвергаются;
  составной FK в БД не даёт связать транзакцию с чужим счётом или другой валютой.
* Тесты изоляции по всем ресурсам; мутационные проверки (убрать фильтр владельца →
  тесты падают).

### Нарушение аутентификации — защищено, с замечаниями
* Argon2id; JWT HS256/384/512, `alg=none` и чужая подпись отвергаются, `exp`
  обязателен; access 30 мин; refresh — серверный, ротация, обнаружение повторного
  использования (отзыв семейства); logout-all и смена пароля мгновенно аннулируют
  access-токены (`token_version`); выравнивание времени ответа при неизвестном e-mail.
* Rate limit входа: по IP (20/мин) **и** по аккаунту (10/15 мин, ключ — хеш e-mail).
* MEDIUM: регистрация отвечает 409 на занятый e-mail (перебор адресов) — смягчено
  лимитом 10 регистраций/час с IP.
* LOW: нет `iss`/`aud` в JWT; нет MFA; refresh-токены не чистятся фоновой задачей.

### Утечка чувствительных данных — защищено, с замечаниями
* Ответы не содержат хешей паролей и секретов (тесты, проверка OpenAPI).
* Ошибки 500 — общий текст + `request_id`; внутренности только в логах.
* Логи: без тел запросов, query string, IP, токенов, сумм, вопросов к AI (тест).
* Заголовки: `Cache-Control: no-store`, CSP, nosniff, `X-Frame-Options`, HSTS в
  production; `/docs` выключены в production; заголовок `Server` убран.
* Номера карт и ИИН маскируются в описаниях импорта и вопросах к AI; в LLM не
  уходят имена/e-mail/названия пользовательских категорий.
* HIGH (→ B1, B5): данные at-rest не шифруются приложением; агрегаты финансов
  уходят LLM-провайдеру, если он включён.

### Небезопасная загрузка файлов — защищено
* Формат по содержимому; лимиты размера (5 МБ) и строк; отказ при макросах,
  внешних ссылках, zip-бомбах; defusedxml; файл не сохраняется; разбор в потоке.
* Общий лимит тела запроса: 1 МБ (JSON), загрузки — 5 МБ + накладные; проверка и
  по `Content-Length`, и при потоковой передаче (chunked).

### Обход rate limiting — защищено, с замечаниями
* Production требует Redis (общие счётчики для всех воркеров/реплик); in-memory
  запрещён настройками.
* IP клиента берётся только из `request.client` (uvicorn `--proxy-headers` +
  `FORWARDED_ALLOW_IPS` = только прокси); приложение не читает `X-Forwarded-For`.
* Сбой Redis: auth — fail-closed (503), остальное — fail-open с логом.
* MEDIUM: фиксированное окно допускает до 2× лимита на границе окон; ротация
  IPv6-адресов обходит лимит по IP (но не лимит по аккаунту).

### Утечка секретов — защищено
* История git проверена: секретов и `.env` нет. `.env`, `secrets/`, бэкапы в `.gitignore`;
  `.env` исключён из Docker-контекста.
* `SecretStr` для ключей и URL с паролями; ключ OpenAI только в заголовке запроса.
* Секреты — файлы `/run/secrets`, не переменные окружения образа.

### Небезопасная debug-конфигурация — защищено
* Образ по умолчанию `ENVIRONMENT=production`; production отвергает DEBUG,
  `DB_ECHO`, `LOG_LEVEL=DEBUG`, слабый ключ, `*`/HTTP в CORS, отсутствие Redis.
* Нет `--reload`, `print`, `breakpoint`, `eval`, `pickle`, `subprocess` в `app/`.
* Устаревшие эндпоинты (включая старый советник с рекомендациями ETF без
  дисклеймеров) выключены в production.

### Прочее
* MEDIUM: одна роль БД для миграций и работы приложения — рекомендуется отдельная
  роль runtime без прав DDL.
* MEDIUM: GitHub Actions закреплены по мажорным версиям, не по SHA.
* LOW: превью импорта истекают «лениво»; нет фоновой очистки.
